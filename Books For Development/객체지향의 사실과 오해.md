# 1장 : 협력하는 객체들의 공동체 

1. 실세계의 모방이라는 객체지향의 개념은 훌륭한 프로그램을 설계하고 구현하는 실무적인 관점에서는 부적합하지만 객체지향이라는 용어에 담긴 기본 사상을 이해하고 학습하는 데는 매우 효과적이다.
   - 가만 보면 항상 실세계와 연관 짓는 예제가 많았다.

2. 여러분은 객체지향에서 가장 중요한 개념 세 가지를 이미 이해했다는 점이다. 그것은 바로 **역할, 책임, 협력이다.**
   - 어떤 객체도 섬이 아니다.
   - 프로그램 안에는 많은 객체가 존재한다.  그 객체들끼리 상호 작용을 하고 이를 작가는 협력으로 표현했다.

3. 실행중인 app의 내부를 눈으로 직접 볼 수 있다면 그 안에는 쉴 새 없이 메시지를 주고받으며 협력하는 객체가 존재한다는 것을 확인할 수 있을 것 이다.

4. 객체는 다른 객체의 요청에 충실히 귀 기울이고 다른 객체에게 적극적으로 도움을 요청할 정도로 열린 마음을 지녀야 한다. 외부의 도움을 무시한 채 모든 것을 스스로 처리하려고 하는 전지전능한 객체는 내부적인 복잡도에 의해 자멸하고 만다.
   - 프로그램은 많은 객체가 존재하니까 결국 다른 객체랑 함께 뭔가를 해야 한다.

5. 작가가 정리한 객체지향
   - 객체지향이란 시스템을 상호작용하는 자율적인 객체들의 공동체로 바라보고 객체를 이용해 시스템을 분할하는 방법이다.
   - 자율적인 객체란 **상태와 행위를 함께 지니며 스스로 자기 자신을 책임지는 객체를 의미한다.**
   - 객체는 시스템의 행위를 구현하기 위해 다른 객체와 협력한다. 각 객체는 협력 내에서 정해진 역할을 수행하며 역할은 관련된 책임의 집합이다.
   - 객체는 다른 객체와 협력하기 위해 메시지를 전송하고, 메시지를 수신한 객체는 메시지를 처리하는 데 적합한 메서드를 자율적으로 선택한다.

6. 내 생각 정리
   - 객체 끼리 협력해서 프로그램을 만드는 것이 객체 지향.
   - 객체의 상태는 멤버 변수 같고, 행위는 메서드 같다.
   - 객체가 메시지를 전송하는 정확한 예제가 무엇일까?

# 2장 : 이상한 나라의 객체

1. 객체지향 패러다임의 목적은 현실 세계를 모방하는 것이 아니라 현실 세계를 기반으로 새로운 세계를 창조하는 것이다.
   - 현실에서 있을 수 없는 현상이 소프트웨어에서는 가능하다.
   - 자동차가 스스로 시동을 걸기 -> 자동차 객체에 본인의 시동 변수를 true로.

2. 메시지(Message)
   - 객체지향에서 **'Send a Message'라는 개념이 나오는데 이는 'calling a method'와 같다.**
   - 어떤 객체가 현재 객체에게 어떤 메시지를 전달한다. 어떤걸 해달라고. 현재 객체는 이를 수행해야 할 의무가 있다. 그러므로 메서드로 구현한다.
   - **메시지 전달 = 메소드 호출**

3. 객체의 다양한 특성을 효과적으로 설명하기 위해서는 객체를 **상태(state), 행동(behavior), 식별자(identity)**를 지닌 실체로 보는 것이 가장 효과적이다.

4. 상태(state)
   - 어떤 일의 발생 여부를 지금까지의 행동으로 판단하는 것은 매우 복잡하고 어렵다. 예를 들어 엘리스가 어떤 문을 통과할 수 있는지에 대한 판단을 행동으로 판단한다고 가정해보자. 그러면 프로그램은 엘리스의 키와 관련된 모든 행동을 조사해야 하고 이는 엄청난 과부하를 가져온다. 하지만 **엘리스의 키(상태) 값만 조사하면 바로 판단할 수 있다.**
   - 숫자, 문자열, 양, 속도, 시간, 날짜, 참/거짓 같은 단순한 값들은 객체가 아니다. 단순한 값들은 그 자체로 독립적인 의미를 가지기보다는 다른 객체의 특성을 표현하는 데 사용된다. 다시 말해 다른 객체의 상태를 표현하기 위해 사용된다.
      - **상태는 멤버 변수**라고 생각하면 될 것 같다.
      - 상태는 특정 시점에 객체가 가지고 있는 정보의 집합

5. 행동(Behavior)
   - 행동은 다른 객체로 하여금 간접적으로 객체의 상태를 변경하는 것을 가능하게 한다.
   - **행동은 method**라고 생각하면 될 것 같다.

6. 캡슐화(Encaptulation) = 상태 캡슐화 = 멤버 변수 캡슐화 (p55 ~ P57)
   - 캡슐화의 일반적인 정의
      - 클래스를 생각해보면 속성(field = property = state) 영역이 있고 아래에 method들이 존재하는 건 익히 알고 있다.
      - 은닉은 결국 정보은닉이고, private & public을 의미한다. 여기까지가 기존의 캡슐화의 개념이다.
   - **객체는 상태를 캡슐 안에 감춰둔 채 외부로 노출하지 않는다. 객체가 외부에 노출하는 것은 행동뿐이며, 외부에서 객체에 접근할 수 있는 유일한 방법 역시 행동뿐이다.**
      - 객체의 멤버 변수를 다른 객체가 바로 사용할 수 없도록 한다. 현재 객체에서 다른 클래스의 객체가 사용할 수 있는 것은 언제나 메소드. 그러므로 객체의 멤버 변수를 참조할 때도 객체의 메소드를 이용해야 한다.
      - get, set의 존재 이유라고 생각한다.
   - 상태를 외부에 노출시키지 않고 행동을 경계로 캡슐화하는 것은 결과적으로 **객체의 자율성을 높인다.** 자율적인 객체는 스스로 판단하고 스스로 결정하기 때문에 객체의 자율성이 높아질수록 객체의 지능도 높아진다. 결론적으로 상태를 잘 정의된 행동 집합 뒤로 캡슐화하는 것은 객체의 자율성을 높이고 협력을 단순하고 유연하게 만든다. 이것이 상태를 캡슐화해야 하는 이유다.

7. 객체지향 설계자로서 우리의 목적은 현실을 모방하는 것이 아니다. 단지 이상한 나라를 창조하기만 하면 된다. 현실을 닮아야 한다는 어떤 제약이나 구속도 없다.

8. 종합
   - 클래스를 만들 때 상태(변수)와 행동(메서드)을 구분하여 코딩한다.
   - 상태는 캡슐화의 개념에 따르면 외부로 노출하지 않아야 하기 때문에 private또는 public(get;private set;)으로 선언한다.

# 3장 : 타입과 추상화

1. 앨리스는 정원사들, 병사들, 왕자와 공주, 하객으로 참석한 왕과 왕비들, 하트 왕과 하트 여왕의 차이점은 과감하게 무시한 채 공통점만을 취해 단순화해버렸다. '기껏해야 트럼프에 불과해'라고 읊조리는 마지막 대사에서 앨리스는 정원에 서있는 다양한 인물들을 계급, 나이, 성격 등의 차이점은 무시한 채 '트럼프'라는 유사성을 기반으로 추상화해서 바라보고 있는 것이다. 이처럼 공통점을 기반으로 객체들을 묶기 위한 그릇을 개념이라고 한다.
   - 공통점을 취하고 세부적인 차이는 무시한다.

2. 분류란 객체에 특정한 개념을 적용하는 작업이다. 객체에 특정한 개념을 적용하기로 결심했을 때 우리는 그 객체를 특정한 집합의 멤버로 분류하고 있는 것이다.

3. 타입은 개념과 완전히 동일하다. (아래의 내용을 이해하기 위한 초석이다.)

4. **객체를 분류하는 기준은 타입**입니다. 타입을 나누는 기준은 객체가 수행하는 행동이라는 사실만을 기억하기 바란다. 객체를 분류하기 위해 타입을 결정한 후 프로그래밍 언어를 이용해 **타입을 구현할 수 있는 한 가지 방법이 클래스**라는 사실을 아는 것만으로도 충분하다.
   - 작가가 설명하는 정원사들, 병사들, 왕자와 공주, 하객으로 참석한 왕과 왕비들, 하트왕과 하트 여왕은 객체다. 그리고 이들을 트럼프라는 개념으로 하나에 묶어 분류했다. 이러한 개념을 프로그래밍 관점으로 보면 타입이고 이를 언어로 구현하는 방법 중 하나가 클래스다.
   - 위에서 나열한 나의 이론을 정리하면 객체들이 같은 행동을 한다면 이 객체들의 공통 행동을 묶어 하나의 클래스로 구현할 수 있다.
   - 지금까지는 클래스를 만들고 객체를 생각했는데 이제는 클래스를 만들기 전에 이 클래스가 게임 세상에서 어떤 객체들의 공통적인 행동을 포괄할 수 있는지 고민해야 할 것 같다.
   - 클래스에 대한 내용은 P104, P236 참고

5. 객체가 어떤 행동을 하느냐에 따라 객체의 타입이 결정된다. 객체의 내부 표현 방식이 다르더라도 **어떤 객체들이 동일하게 행동한다면 그 객체들은 동일한 타입에 속한다.객체의 타입을 결정하는 것은 객체의 행동뿐이다.**(작가는 이 문구를 10번이나 적고 강조했다) 어떤 객체들이 동일한 행동을 수행할 수 있다면 그 객체들은 동일한 타입으로 분류될 수 있다. 객체를 결정하는 것은 행동이다.
    - 적군 객체들을 만든다고 가정할 때 적군 객체 마다의 속성은 다르지만 크게 보면 같은 행동을 한다. (아군 공격)

6. 일반적인 타입은 특수한 타입에 비해 더 적은 수의 행동을 가지며 특수한 타입은 일반적인 타입에 비해 더 많은 행동을 가진다. 단, 특수한 타입은 일반적인 타입이 할 수 있는 모든 행동을 동일하게 수행 할 수 있어야 한다.
   - 일반적인 타입 = Supertype
   - 특수 타입 = Subtype
     - 일반적인 타입에 대한 프레임워크를 구현하고 내부의 많은 함수들을 가상함수로 구현하는 게 좋지 않을까

7. 나의 생각 저장소
   - 객체들의 관계를 이용해서 상속과 컴포넌트 패턴에 대하여 정리해보자.
   - 세상에 존재하는 객체를 분류하는 방식. 추상화해서 겹치는 부분에 대한 관계를 만들기.
   - 이 장의 초반 80%는 객체들의 공통적인 특성으로 클래스를 구현하는 것을 설명하고, 후반 20%는 클래스(=타입)들의 계층을 나누는 법을 설명하고 있고 이를 상속으로 설명하고 싶어하는 것 같다.

3. 어떤 객체가 수행하는 책임의 집합은 객체가 협력 안에서 수행하는 역할을 암시한다.

# 5장 : 책임과 메시지
1. **객체가 어떤 행동을 하는 유일한 이유는 다른 객체로부터 요청을 수신했기 때문**이다. **요청을 처리하기 위해 객체가 수행하는 행동을 책임**이라고 한다.
   - 다른 객체로부터 메시지를 받고, 현재 객체가 해당 메시지를 수행할 능력이 있다면 적절한 메서드를 선택해 수행할 책임이 있다.
   - **책임을 구현하는 것이 메서드**라고 생각한다.
  - P141 ~ P144

2. 앨리스 이야기로 작가가 설명하는 자율적인 책임 : 왕은 목격자인 모자 장수에게 '증언하라'라는 요청을 전송한다. 모자 장수가 재판이라는 협력에 참여하기 위해서는 왕의 요청을 적절하게 처리한 후 응답해야 한다. 요청은 수신자의 책임을 암시하므로 모자 장수는 재판이라는 협력에 참여하기 위해 '증언할' 책임을 진다. **왕은 모자 장수가 '증언하라'라는 자신의 요청에 반응해 책임을 완수할 수만 있다면 어떤 방법으로 증언하는지에 관해서는 신경을 쓰지 않는다.**
   - 왕이 모자장수에게 요청하는 메시지의 추상 정도에 따른 결과
      - 증언하라 : 모자 장수는 왕의 요청을 받아야만 책임을 수행하기 시작하겠지만 증언 방식이나 증언에 필요한 자료는 스스로의 의지와 판단에 따라 자유롭게 선택할 수 있다.
      - 목격했던 장면을 떠올려라, 떠오르는 기억을 시간 순서대로 재구성해라 : 상세한 수준의 요청은 '증언'이라는 협력의 최종목표는 만족시킬지 몰라도 모자 장수가 누려야 하는 선택의 자유를 크게 훼손하고 만다.
   - 우리는 적절히 메시지의 추상 정도를 조절해야 한다?
