# 예측할 수 없는 일정 관리
- 주니어는 주어진 업무를 받았을 때 얼마나 걸릴지 예측을 할 수 없다. 그게 되는 순간이 시니어라고 배웠다.
- 그러면 주니어가 그나마 예측을 하기 위해서는 어떻게 해야 할까?
  - :star:**일정 초반에 야근을 한다!**
  - 초반에 일을 평소 보다 많이 한다면 당연히 일은 더 많이 처리하게 된다. 그러다보면 일정의 마감이 주니어여도 보인다.
  - 물론 초반에 몸이 상할 수 있다. 적절히 유도리 있게 시간을 배분해라.

# 데이터는 한 곳에 모아 놓고 참조한다.
- 데이터를 모아 놓은 파일이 있고 이를 참조로 가져온다. 
- 데이터를 호출하고 갱신하는 시점도 중요하다. 프로그램의 실행 흐름을 완벽히 조절할 수 는 없지만 올바른 호출 위치는 존재한다. 그러므로 올바른 호출 위치에서 메서드를 호출한다.

# 주니어와 시니어의 다른 점
- 주니어는 필요한 정보가 있으면 그냥 멤버 번수나 매개 변수 추가 같이 쉬운 방법을 택한다. 하지만 시니어는 프로그램 전체에 필요한 지에 대한 생각과 유지 보수 까지 생각하고 최대한 이 것에 포커스를 맞춰 필요한 정보를 처리한다.
  
# 우선 순위

# 재사용이 가능한 메서드를 만들기 위해서 필요한 역량 : 코드 흐름 파악
- 4가지 클래스에 존재하는 각각의 메서드에서 사용하는 어떤 메서드를 구현한다고 가정하자. 
- 재사용해야 하는 메서드가 어떤 기능이 필요하고 이를 구현하기 위해 필요한 매개변수와 동작을 설계한다. 호출하는 각각의 스크립트가 어떤 메서드로 구성되어 있고, 어떤 클래스인지를 파악하면 이 메서드에 전달 할 수 있는 매개변수를 알 수 있다. 
- EX : 나는 각기 다른 사람 4명을 소개하는 글을 작성해야 한다. 4명에게서 공통적으로 필요한 정보를 알아내려고 한다. 그러려면 나는 기본적으로 4명과 각각 이야기를 해보며 그들이 어떤 사람인지 이해하고 각각의 개성에서 공통적으로 뽑아낼 수 있는 내용을 만들어야 한다. 1번 사람과 대화를 하고 글을 작성하면 2~4번과 대화하면 계속 생각이 바뀌고 코스트가 발생한다.   

# 하드 코딩에 대한 오해
- :star:**기획자님들이 만들어 주는 데이터 시트에서 ID(key)를 내가 직접 적는 것은 하드 코딩이 아니다.**
- 이건 너무 당연한거다. 생각해보면 웃기다. 그럼 Key를 어떻게 찾을 건데?

# 필요한 값 가져오기에 대한 오해
- 만약 A Script에서 필요한 데이터가 아무 관련 없는 B Script에 있다고 가정하자. A에서 코딩을 해서 필요한 데이터를 가져올 수 있다. 하지만 B에 이미 그에 대한 기능이 있다. 당연히 연관된 스크립트라면 A에서 이를 재사용하는 게 옳지만 그렇지 않는다면 굳이 B의 해당 기능을 가져올 필요는 없다.

# 사소한 최적화 때문에 시간 낭비하지 말자.
- List를 몇 번 만들어서 메서드를 실행하는 것에 대한 두려움을 갖지 말자. List 만드는 데 큰 코스트가 들지 않으면 가독성을 위해서라도 몇 번 만들어도 된다. 괜한 작은 코스트에 긴 설계 시간을 두어 업무의 속도를 늦추지 말자.

# 메서드를 분할해서 새로운 메서드를 만드는 것에 대해 생각해 볼 점
- 나는 클린 코드를 읽고 하나의 메서드는 하나의 기능을 하고 단순해야 함에 빠져버렸다. 그래서 이를 넘어서 쓸 데 없이 메서드를 분할 하는 경우도 있다.
- 예를 들어 A 메서드에서 참조 변수로 Animal을 참조했다고 하자. 근데 A 메서드가 너무 길어서 B 메서드로 분할 했다. 근데 B 메서드에서 Animal 참조 변수가 필요해서 또 참조했다. 이러면 안 된다.
  - 분할을 하지 말던가
  - 참조 변수를 매개변수로 넘겨주던가
    - 근데 이러면 매개변수가 증가하는 단점이 생긴다.
