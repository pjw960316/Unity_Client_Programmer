# 개발자에게 궁금증이란?
- 람다식을 보고 시니어 분들이 쓰니까 써야겠다가 아니라 왜 람다가 좋은지, 람다가 뭔지, 이런 걸 찾아보고 개발자 분들과 공유하는 게 클라이언트 개발자다.
- **왜? -> 구글링 -> 이해**

# 예측할 수 없는 일정 관리
- 주니어는 주어진 업무를 받았을 때 얼마나 걸릴지 예측을 할 수 없다. 그게 되는 순간이 시니어라고 배웠다.
- 그러면 주니어가 그나마 예측을 하기 위해서는 어떻게 해야 할까?
  - :star:**일정 초반에 야근을 한다!**
  - 초반에 일을 평소 보다 많이 한다면 당연히 일은 더 많이 처리하게 된다. 그러다보면 일정의 마감이 주니어여도 보인다.
  - 물론 초반에 몸이 상할 수 있다. 적절히 유도리 있게 시간을 배분해라.

# 데이터는 한 곳에 모아 놓고 참조한다.
- 데이터를 모아 놓은 파일이 있고 이를 참조로 가져온다. 
- 데이터를 호출하고 갱신하는 시점도 중요하다. 프로그램의 실행 흐름을 완벽히 조절할 수 는 없지만 올바른 호출 위치는 존재한다. 그러므로 올바른 호출 위치에서 메서드를 호출한다.

# 주니어와 시니어가 메서드를 만들 때 생각 하는 다름
- 주니어는 필요한 정보가 있으면 그냥 멤버 번수나 매개 변수 추가 같이 쉬운 방법을 택한다. 하지만 시니어는 프로그램 전체에 필요한 지에 대한 생각과 유지 보수 까지 생각하고 최대한 이 것에 포커스를 맞춰 필요한 정보를 처리한다.
  
# 우선 순위
- 일에는 우선순위가 있다. 우선순위 대로 일을 처리하는 것도 중요하다. 

# 재사용이 가능한 메서드를 만들기 위해서 필요한 역량 : 코드 흐름 파악
- 4가지 클래스에 존재하는 각각의 메서드에서 사용하는 어떤 메서드를 구현한다고 가정하자. 
- 재사용해야 하는 메서드가 어떤 기능이 필요하고 이를 구현하기 위해 필요한 매개변수와 동작을 설계한다. 호출하는 각각의 스크립트가 어떤 메서드로 구성되어 있고, 어떤 클래스인지를 파악하면 이 메서드에 전달 할 수 있는 매개변수를 알 수 있다. 
- EX : 나는 각기 다른 사람 4명을 소개하는 글을 작성해야 한다. 4명에게서 공통적으로 필요한 정보를 알아내려고 한다. 그러려면 나는 기본적으로 4명과 각각 이야기를 해보며 그들이 어떤 사람인지 이해하고 각각의 개성에서 공통적으로 뽑아낼 수 있는 내용을 만들어야 한다. 1번 사람과 대화를 하고 글을 작성하면 2~4번과 대화하면 계속 생각이 바뀌고 코스트가 발생한다.   

# 하드 코딩에 대한 오해
- :star:**기획자님들이 만들어 주는 데이터 시트에서 ID(key)를 내가 직접 적는 것은 하드 코딩이 아니다.**
- 이건 너무 당연한거다. 생각해보면 웃기다. 그럼 Key를 어떻게 찾을 건데?

# 필요한 값 가져오기에 대한 오해
- 만약 A Script에서 필요한 데이터가 아무 관련 없는 B Script에 있다고 가정하자. A에서 코딩을 해서 필요한 데이터를 가져올 수 있다. 하지만 B에 이미 그에 대한 기능이 있다. 당연히 연관된 스크립트라면 A에서 이를 재사용하는 게 옳지만 그렇지 않는다면 굳이 B의 해당 기능을 가져올 필요는 없다.

# 사소한 최적화 때문에 시간 낭비하지 말자.
- List를 몇 번 만들어서 메서드를 실행하는 것에 대한 두려움을 갖지 말자. List 만드는 데 큰 코스트가 들지 않으면 가독성을 위해서라도 몇 번 만들어도 된다. 괜한 작은 코스트에 긴 설계 시간을 두어 업무의 속도를 늦추지 말자.

# 메서드를 분할해서 새로운 메서드를 만드는 것에 대해 생각해 볼 점
- 나는 클린 코드를 읽고 하나의 메서드는 하나의 기능을 하고 단순해야 함에 빠져버렸다. 그래서 이를 넘어서 쓸 데 없이 메서드를 분할 하는 경우도 있다.
- 예를 들어 A 메서드에서 참조 변수로 Animal을 참조했다고 하자. 근데 A 메서드가 너무 길어서 B 메서드로 분할 했다. 근데 B 메서드에서 Animal 참조 변수가 필요해서 또 참조했다. 이러면 안 된다.
  - 분할을 하지 말던가
  - 참조 변수를 매개변수로 넘겨주던가
    - 근데 이러면 매개변수가 증가하는 단점이 생긴다.

# 협업 에러
- 테스트 결과 올바르게 동작했고 서밋한 코드가 있다. 그게 3일 뒤에 변경사항이 없음에도 정상적으로 동작하지 않았다.
  - 먼저 그 사이에 내가 정말 아무 작업을 하지 않았는지 검증한다.
    - 로컬에서 그냥 연습했을 수 도 있다.
    - 최신화를 하지 않았을 수도 있다.
  - 하지만 정말 동작하지 않는다면 그 사이에 다른 누군가의 서밋으로 인한 side-effect일 수도 있다.
    - 개인의 프로젝트에서는 발생할 수 없는 에러지만 협업에서는 발생할 수 있다.
    - 이는 서밋로그를 분석하고 주변에 질문을 해서 해결해야 한다.

# 코드 분석과 콜스택 분석
- 결국에 코드가 어떻게 돌아가는지를 이해하는 방식이다.
- 기존에는 큰 흐름을 일단 파악하고 -> 내부의 세부적인 로직이 어떻게 돌아가는지를 분석했었다.
  - 물론 더 못할 때는 큰 흐름만 대충 파악하고 코딩을 했다.
- 하지만 이 방식도 좋지 않다.
  - 결국 **세부적인 로직이 어떻게 돌아가는지를 알아보는 게 중요하다.**
    - 예를 들어 서버 통신이라면 서버 통신 관련 클래스가 존재할 것 이고 내부 메서드가 존재할 것 이다. 내부 메서드를 하나하나 다 보라는 것이 아니다.
    - 내부 메서드를 사용하는 녀석이 있다면 그 메서드를 해당 클래스에서 왜 사용하고 어떻게 사용하는지 정도는 세부적으로 파악해야 한다는 것 이다.
      - 이게 결국 다른 메서드에서 호출되는 메서드면 해당 클래스의 주요 메서드가 될 것 이고 이를 이해하면 클래스 자체를 이해할 것 이다.
- 너무 지엽적인 것은 지양하자.
  - 주니어가 판단해도 이것 까지 분석할 필요가 없는 메서드도 있다. 예를 들어 서버에서 메시지를 만드는 문법에 대한 메서드는 굳이... 라는 생각이 든다.
  - 이렇게 지엽적으로 파고 들면서 이해할 필요는 없다.
- 어떤 메서드가 호출되었고 해당 메서드를 담고 있는 클래스에 대해서 최소한 분석해야 할 것
  - 클래스가 뭘 상속 받고 있고.
  - 뭘 정의하고 있고.
  - 어떤 동작을 하기 위해 존재하는지는 파악해야 한다.

# 메서드를 만드는 기준 (정답은 아닐 수 있다.)
- :star:**메서드는 최소한 2번 이상 사용될 때 가치가 있다.**
  - 재사용의 '재'가 뭔지 생각해보면 너무 자명하다.
- 이 기능은 죽어도 한 번만 쓸 것 같으면 굳이 뺄 필요 없다. 한 번은 재사용이 아니니까.
  - 확장성에 대한 반발이 있을 수 있으나 정말 절대 다시 안 쓸 것 같고 여기서만 쓸 것 같은 기능은 존재한다.
  - 그리고 메서드가 너무 많아도 왔다갔다 하며 코드를 읽게 되므로 과하면 가독성도 해친다고 생각한다.

# 코드 리딩을 잘하는 팁
- **큰 흐름 파악은 당연히 해야 하는 것** 이다.
- **왜 이렇게 구조를 잡았을 지에 대해 궁금해 하는 것이 제일 중요하다.**
- 메서드 하나 하나를 딥하게 이해하는 것 보다는 동작방식을 간단히 이해하고 그 구조에서 왜 이런 구조를 잡았는지가 중요하다.
  - 메서드는 **그 메서드를 쓸 때 정확히 이해하는 것**은 중요하다. 하지만 클래스의 모든 메서드를 하나 하나 씩 딥하게 이해할 필요는 없다.
- 유니티에서 제공하는 메서드에 대한 궁금증이 있다면 해당 메서드를 구글에 검색해서 메서드의 동작 방식을 이해하자.
  - 해당 메서드 자체에 콜백 구조가 숨겨져 있는 경우도 있다.
