## :fire: 왜 콜백을 쓰는가? -> 단방향 의존성을 구현하기 위해, 그리고 결과 발생 시점을 호출받는 쪽에 맡기기 위해!
- 두 클래스가 서로를 필드로 들고 있으면 양방향 의존성이 생긴다. 서로가 강하게 의존되며 서로가 없으면 동작이 불가능하다. (null 지옥)
- 그러므로 둘 다 의존성이 없는 게 좋겠지만 그건 현실적으로 불가능하고, 단방향 의존성을 구현해야 한다.
  - A 클래스는 B 클래스를 필드로 들고 있는다.
  - B 클래스는 A 클래스를 필드로 들고 있지 않는다. 단, 콜백을 통해 A 클래스에게 자신의 context를 전달한다.

<br><br>

## :👨‍🔬: 고민 과정
- 단방향 의존성을 설계한 게임에서는 콜백이 정말 많이 쓰인다.
  - delegate / Action / Func , Event, UniRx_Subject, IObservable, Unity Event, Custom Observable Class 정도가 있는 것 같다.
- 하지만, 이 기법들에 대해 어떤 상황일 때 어떤 기법을 쓸지 고민해 본 적이 없다. 그 때 생각 난 걸 그냥 썼던 것 같다. 적어도 '이런 순간에 이걸 사용하자.' 수준의 생각은 해야 하지 않을까?

<br><br>

## :fireworks: 아래에는 n가지의 콜백 기법을 필요한 상황마다 정리했다.

<br><br>

## :one: event 키워드와 사용되는 Action 과 Func
#### 언제 쓸까?
- 구독자 수가 1개 ~ 2개 일 때
- 흐름이 엄청 단순할 때
  - API 수준의 이벤트 조합, 필터링, 시간 제어가 필요하지 않을 때 
  - 과설계를 방지해준다.
- 명시적으로 +=, -= 관리해도 충분히 추적 가능해서 Disposable 관리가 필요하지 않을 때

<br>

#### :👨‍🔬:event 키워드가 없는 Action 과 Func를 필드로 만들지 말자??
- 외부에서 Invoke를 할 수 있게 되는데 그건 유지보수가 되지 않는 위험한 코드가 아닐까

<br><br>

## :two: UniRx
#### 언제 쓸까?
- 이벤트를 스트림처럼 조합해야 할 때
- 여러 이벤트를 합치거나 변환해야 할 때
- 특정 조건에서만 받고 싶을 때
- 시간 기반 처리(Throttle, Delay, Timer 등)가 필요할 때
- 구독 생명주기를 CompositeDisposable로 묶어 관리하는 편이 더 안전할 때
