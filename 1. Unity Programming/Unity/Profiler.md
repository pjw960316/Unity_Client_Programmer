# 프로파일링을 해야 하는 이유
- 여기서 부하가 걸릴 것 같다.
  - **이런 태도는 좋지 않다. 감히 프로파일링을 하지 않고 정확한 부하를 예측할 수 있는가?**
- 부하가 걸리는 정확한 메서드와 부하의 정도를 알면 효율적으로 부하를 제거 할 수 있다.
  - 부하가 클 것 으로 예측된 코드를 수정했는데 실제로는 미비 했을 수도 있다.
  - 프로그래머의 감 보다는 프로파일링 결과 수치를 믿어야 한다.

# 어쩔 수 없는 부하에는 매몰 되지 말아야 한다.
- 모든 자원은 타협이다.
- 게임 오브젝트 100개를 생성하면 렉이 걸린다. 
  - 최적화는 가능하지만 100개를 생성하는 오버헤드가 0초가 되는 것은 불가능에 가깝다.
    - 스크롤로 100개의 오브젝트를 보여주는 경우, 일반 스크롤을 사용하면 100개를 모두 생성하고 창을 띄우기 때문에 최초에는 렉이 발생하지만 스크롤 상황에서는 부하가 적다. 
    - 하지만 OSA를 이용해서 화면에 보이는 오브젝트만 생성하면 초기에 바로 생성되지만 스크롤 상황마다 렉이 발생한다. 그러므로 적절한 방식을 채택해야 한다.

# Hierarchy View
- ![Alt text](./Capture/20231108_111445.png)
- 프레임이 튀는 부분에서 해당 메서드가 얼마 만큼의 퍼센트를 차지 하는 지 확실히 알 수 있다.
- TimeLine View 보다 면밀히 분석하기 좋은 View 모드라고 생각한다.
- 프로파일링 단계에서 로그를 출력하는 부분은 생각보다 많은 퍼센트를 차지 하는 것을 확인 했다. 그러므로 프로파일링을 할 때는 반드시 로그 출력을 끄고 진행한다.
  - Conditional Attribute 를 이용해서 로그를 끄는 방식을 채택한다.

# TimeLine View
- ![Alt text](./Capture/20231013_160558.png)
- 계층 구조다.
  - 맨 위에 있는 블록을 1단계로 쪼개면 그 아래 블록이고, 그 블록들을 또 쪼개면 아래 블록들로 이루어진다.
  - 예를 들어 200ms가 걸리는 어떤 함수를 발견했다. 그 함수는 2가지 기능으로 이루어져서 한 기능이 120ms, 다른 하나가 80ms를 동작시키면 200ms 함수 아래에 2개의 블록이 각각 120ms와 80ms로 존재할 것 이다.
- 파란색 블록은 스크립트를 의미하고 7호선 색 블록은 엔진 코드를 의미하므로 실질적으로 눈여겨 볼 항목은 파란색 블록이다.
  - 파란색 블록이 스크립트를 담당하므로 내가 작성한 스크립트와 메서드 이름이 블록위에 적혀있다.
