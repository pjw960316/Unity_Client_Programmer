## :sparkles: YAGNI를 고민하게 된 개발 경험

#### :white_check_mark: 경험

- 미리 만든 자료구조의 예상 용도와 실제 쓰임
- 쓰지 않는 구조가 관리 대상으로 남았을 때의 불편
- 개발 → 리팩터링 → 개발 → 리팩터링을 반복하며 전체 개발이 늦어졌던 경험

## :sparkles: 내가 구현에서 YAGNI를 적용하는 기준

#### :white_check_mark: 미리 만들기와 필요할 때 만들기

- 미리 만들면 줄어드는 재작업과 늘어나는 관리 부담
- 필요할 때 만들면 더 분명해지는 요구와 그때 감수할 재작업
- 내가 ‘필요할 때 만들기’를 기본으로 택한 이유

<br>

#### :white_check_mark: 구현을 멈추고 설계로 돌아가는 순간

- Codex + Rider에서 정해 둔 설계에 집중하는 이유
- 구현 도중 놓친 점이 보이면 Codex + 노트로 돌아가는 기준
- 재설계 후 원안을 유지할 때와 구현 방향을 바꿀 때

<br>

#### :pushpin: 내가 경계하는 두 가지 실수

- 지금 필요한 변경을 YAGNI라는 이유로 덮는 것
- 언젠가 쓸 가능성만으로 구현 범위를 넓히는 것

## :sparkles: 현재에 집중한다는 내 가치관

#### :white_check_mark: 경험
