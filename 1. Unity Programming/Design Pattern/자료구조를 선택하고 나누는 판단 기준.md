## :sparkles: 이 문서에 기록하려는 내용

- 개발 중 자료를 어떻게 담을지 고민하고, 자료구조를 선택하거나 나눈 이유를 기록한다.
- 자료를 읽고 수정할 때 어떤 점이 복잡했는지, 그 복잡함을 줄이기 위해 어떤 기준을 선택했는지 남긴다.
- 앞으로 개발하면서 판단이 달라지면 그 이유도 함께 보완한다.

<br><br>

## :sparkles: 자료를 담는 구조가 어렵고 복잡해지지 않도록 한다.

- 자료를 담는 구조 자체를 이해하는 데 너무 많은 노력이 들면 안 된다고 생각한다.
- 하나의 구조로 억지로 묶어 복잡해진다면, 자료구조를 나누고 메모리를 더 사용하는 선택도 고려한다.
- 적어도 직렬화해서 보관할 데이터와 런타임에서만 사용할 데이터는 구분한다.

<br><br>

## :sparkles: 동물 스폰 설정 — 복합 Value 대신 같은 Key의 Dictionary로 나누기

#### 경험

- 동물 스폰에는 동물 종류별 Prefab과 스폰 가중치가 필요하다.
- 현재 `FieldObjectAnimalSpawner`에서는 두 값을 각각의 Dictionary에 보관하고, 같은 `EFieldObject`로 연결해 사용한다.

#### :sparkles: 하나로 묶는 방식과 나누는 방식

두 값을 하나로 묶으면 다음과 같은 구조가 된다. 기존 초안에서는 이 방식을 검토하고 있었다.

```text
EFieldObject → AnimalSpawnSetting
                 ├─ Prefab
                 └─ Weight
```

<br>

현재 구현은 다음처럼 값을 나누어 보관한다.

```csharp
[SerializeField] private SerializedDictionary<EFieldObject, FieldObjectAnimalBase> _animalPrefabDict = new();
[SerializeField] private SerializedDictionary<EFieldObject, int> _animalSpawnWeightDict = new();
```

- 현재 프로젝트에서 사용하는 타입은 `AYellowpaper.SerializedCollections.SerializedDictionary`다.
- Inspector에서 편집하는 설정은 각각 보관하고, 사용할 때 같은 Key로 필요한 값을 찾는다.
- 스폰 가중치로 동물별 생성 개수를 계산한 뒤, 해당 동물의 Key로 Prefab을 찾아 생성한다.

<br>

#### :sparkles: 이 사례에서 남길 판단 기준

- 관련된 값이라고 해서 반드시 하나의 Value 클래스로 묶어야 하는 것은 아니다.
- 하나로 묶으면서 직렬화와 Inspector 편집이 복잡해진다면, 단순한 값별로 나누는 선택을 검토한다.
- 이때 Dictionary 개수가 늘어나는 것과 같은 Key를 맞춰 관리하는 부담도 함께 생긴다.

<br><br>

## :sparkles: Codex 보완 제안 — 나눈 뒤의 관리 비용도 확인하기

- 분리한 Dictionary에서 함께 사용할 Key가 일치하는지, 필요한 Prefab이 비어 있지 않은지 확인한다.
- 가중치가 유효한지 확인한다. 현재 스폰 계산에서는 0 이하의 가중치를 허용하지 않는다.
- 직렬화할 수 있는 타입이어도, 실제 Inspector 편집 방식과 Dictionary 구현에 맞는지 확인한다.
- 복합 Value를 사용하면 항상 문제가 생기는 것은 아니다. 기존 초안의 직렬화·Inspector 오류 가능성은 확인할 항목으로 남기고, 직접 겪은 오류로 단정하지 않는다.
- 메모리 증가를 감수한다는 생각은 이해하기 쉬운 구조를 우선하겠다는 판단이다. 모든 자료구조를 무조건 나누는 규칙으로 확대하지 않는다.
