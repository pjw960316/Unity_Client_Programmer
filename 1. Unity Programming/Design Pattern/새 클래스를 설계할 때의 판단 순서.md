# 새 클래스를 설계할 때의 판단 순서

> 작성 중인 판단 기준. Notion 데이터를 게임으로 가져오는 작업에 먼저 적용해 보고 수정한다.

## 상황

새 기능을 위해 클래스를 만들어야 할 때, 내부 구현이나 공통 추상화부터 정하면 사용처가 불분명해질 수 있다.

이전에 ApiManager를 먼저 만들었지만, 내가 이해한 코드가 아니어서 현재 목표에 맞게 사용할 수 없었다. 이번에는 게임이 필요로 하는 기능부터 설계한다.

## 선택: 현재 생각하는 순서

1. **사용처**: 게임의 어떤 기능이 어떤 데이터를 필요로 하는가? 이 기능을 호출할 객체는 누구인가?
2. **메서드 계약**: 호출자가 무엇을 입력하고, 성공·실패 시 무엇을 돌려받아야 하는가?
3. **인터페이스**: 구현을 분리해야 할 실질적인 이유가 있는가? 이미 프로젝트에 존재하는 IManager와 별개의 인터페이스가 필요한지도 확인한다.
4. **구현**: 그 계약을 충족할 자료구조와 알고리즘을 고른다. 외부 API라면 HTTP 통신, 인증, JSON 해석을 이 단계에서 결정한다.

클래스의 책임과 데이터의 소유자는 사용처와 메서드 계약을 정할 때 함께 확인한다.

## 근거

- 사용처와 계약이 정해져야 내부 구현이 해결해야 할 문제도 분명해진다.
- 기존의 [클래스 쪼개기는 회사-직원들의 관계와 같다](./클래스%20쪼개기는%20회사-직원들의%20관계와%20같다.md)와 [Manager & Data 클래스 쪼개기](./Manager%20%26%20Data%20클래스%20쪼개기.md)는 클래스 책임을 작게 유지하고 행동과 데이터를 구분하려는 기존 판단이다.
- 이 순서는 현재의 설계 가설이다. 실제 구현 경험을 쌓으며 수정한다.
