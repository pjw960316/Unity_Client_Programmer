## :fire: 게임 전역 설정 데이터의 의미
> 사용자 플레이로 변경되지 않고 개발자 또는 운영자가 결정하며, 동일한 설정 버전을 사용하는 게임 전체에 공통으로 적용되는 데이터다.

- 롤토체스의 8레벨 필요 경험치처럼 같은 패치 안에서는 모든 사용자가 같은 규칙을 사용해야 한다.
- HabitGame의 `MoneyPerRoutineSuccess`, `MoneyPerSiestaMinute`도 게임의 보상 규칙이므로 게임 전역 설정 데이터에 해당한다.
- 사용자가 루틴을 수행하거나 낮잠을 기록했다고 해서 설정값 자체가 달라지지는 않는다.
- 앱 버전이나 서버 설정 버전이 다르면 값이 달라질 수 있으므로, 모든 디바이스에서 영원히 같은 값이라는 의미는 아니다.

<br><br>

## :fire: 데이터는 변경 주체와 생명주기로 먼저 분류한다.

| 데이터 분류 | 변경 주체 | 예시 | 관리 위치 |
| --- | --- | --- | --- |
| 게임 전역 설정 데이터 | 개발자·운영자 | 보상량, 필요 경험치, 확률 | C#, ScriptableObject, 설정 파일, 서버 |
| 사용자 저장 데이터 | 사용자·게임 플레이 | 재화, 루틴 기록, 낮잠 기록 | `persistentDataPath`, 서버 |
| 런타임 임시 데이터 | 실행 중 코드 | 현재 선택, 타이머, 캐시 | 메모리 |

- 같은 XML 형식을 사용하더라도 게임 설정과 사용자 저장 데이터는 책임이 다르다.
- 하나의 값이 두 위치에 중복되면 어느 값이 기준인지 판단하기 어려워진다.
- 따라서 하나의 설정에는 하나의 기준 데이터만 둔다.

<br><br>

## :fireworks: 게임 전역 설정을 관리하는 방법

### :one: `const` : 개발자가 직접 관리하며 <br> 앱 업데이트를 통한 변경으로 충분할 때 사용한다.

**장점**
- 코드를 수정할 수 있는 사람이 값을 바로 바꿀 수 있어 가장 단순하고 통제하기 쉽다.
- 설정 파일, Loader, Deserialize와 외부 데이터 동기화가 필요 없다.
- 컴파일러가 타입과 값을 검사하므로 문자열 변환이나 누락을 걱정할 필요가 없다.

<br>

**단점**
- 핫픽스 패치에 매우 불리하다.
  - 값을 바꾸려면 코드를 수정하고 앱을 다시 배포해야 한다.
  - → 코드 수정 → 클라이언트 다시 빌드 → 앱 패치 필요
- Inspector에서 편집할 수 없으므로 개발자가 아닌 사람이 관리하기 어렵다.
- 컴파일 타임에 결정할 수 있는 상수만 표현할 수 있다.

```csharp
public const int MONEY_PER_ROUTINE_SUCCESS = 500;
public const int MONEY_PER_SIESTA_MINUTE = 10;
```
- `[SerializeField]`는 Unity가 직렬화하는 객체의 인스턴스 필드를 Inspector에서 편집할 때 사용한다.
- 일반 C# 데이터 클래스에 `[SerializeField]`를 붙이는 것만으로는 단독으로 Inspector에 나타나지 않는다.
- GameObject에 `MonoBehaviour`를 붙이지 않고 설정 데이터를 Inspector에서 관리하려면 `ScriptableObject`를 사용한다.

<br><br>

### :two: `ScriptableObject`:  Unity 안에서 설정을 자주 조정하거나 (=값 변경 빈번) <br> 여러 사람이 Inspector에서 편집하고 Unity Object도 함께 참조해야 할 때 사용한다.

**장점**
- GameObject에 Component로 붙이지 않아도 되므로 데이터가 Scene과 실행 구조에 종속되지 않는다.
- Inspector에서 값을 바로 바꾸며 반복해서 테스트할 수 있다.
- 기획자도 데이터를 수정할 수 있고 `Sprite`, `Prefab`, `AudioClip` 같은 Unity Object를 직접 참조할 수 있다.

<br>

**단점**
- Asset을 생성하고 필요한 객체에 참조를 연결해야 한다.
- 수백~수천 행의 데이터를 한꺼번에 정렬하거나 수정하기에는 Spreadsheet보다 불편하다.
  - AI가 해주지 않을까?
- 여전히 핫픽스 패치에 매우 불리하다.
  - 빌드에 포함된 Asset을 변경하려면 일반적으로 앱을 다시 배포해야 한다.

```csharp
[CreateAssetMenu]
public class GameBalanceData : ScriptableObject
{
    public int MoneyPerRoutineSuccess;
    public int MoneyPerSiestaMinute;
}
```

<br><br>

### :three: CSV·JSON·XML:  수백~수천 개의 데이터를 Spreadsheet에서 관리하거나 <br> 기획자가 관리 주체인 경우 사용한다.

**장점**
- Excel과 Google Sheets에서 대량 데이터를 필터·정렬·수식으로 편집하기 좋다.
  - 수백개 ~ 수천개의 단순 데이터
- Unity를 사용하지 않는 다른 팀원들이 다른 시스템과 데이터를 공유할 수 있다.
- 데이터 생성과 변환 과정을 자동화할 수 있다.

<br>

**단점**
- 외부 데이터를 C# 객체로 바꾸는 Import와 Parsing 과정이 필요하다.
- 필수 값, 숫자 범위, 중복 ID, 참조 ID와 데이터 버전을 검증해야 한다.
- Unity Object를 직접 참조하기 어려워 별도의 ID나 경로로 연결해야 한다.

```text
Excel / Google Sheets
→ CSV / JSON / XML
→ Import
→ Validation
→ Runtime Data
```

<br><br>

### :four: 서버 설정: 사용자에게 배포한 뒤에도 앱 업데이트 없이 게임의 값을 변경해야 할 때 사용한다.

**장점**
- 앱을 다시 배포하지 않고 이벤트 보상, 상점 가격, 확률과 라이브 밸런스를 변경할 수 있다.
- 모든 클라이언트가 서버의 현재 설정을 기준으로 사용할 수 있다.

**단점**
- 서버 구축과 운영 비용이 필요하다.
- 네트워크 실패와 클라이언트·서버의 설정 버전 차이를 처리해야 한다.
