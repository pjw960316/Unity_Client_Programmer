## :fireworks: ValueTuple이 Class보다 훨씬 맘이 편하다.

#### :white_check_mark: 경험

- **클래스로 만들면 더 깊게 봐야 할 것 같다.**
  - 이 타입이 어떤 책임을 갖고 있는지 생각하게 된다. 
  - 정작 선언에 필드 두 개만 있으면 그 확인이 귀찮게 느껴진다.
- **스크립트에 데이터 전용 짧은 클래스가 무수히 많아지면 유지보수에 좋을리가 없다.**
  - Codex가 클래스 선언을 금방 만들어 줘도, 나중에 코드를 읽고 이해하는 건 내 몫이다.
  - 단순한 데이터 묶음마다 타입을 만들면 스크립트가 길어지고, 읽으면서 뜻을 확인해야 할 이름도 늘어난다.
  - 값을 묶을 때마다 같은 고민을 하게 되니, 내가 자주 쓰는 경우에 적용할 기준을 정해두고 싶다.
- **메서드 조차 없는 클래스가 메리트를 갖는가?** 

<br>

#### :white_check_mark: 개발 중에 적용해 볼 기준

- **두 값을 함께 쓰고, 필드 이름만 봐도 쓰임이 읽히면 naming valueTuple로 시작한다.**
  - `YearMonth`와 `CheckCount`처럼 두 이름을 읽고 바로 다음 줄로 넘어갈 수 있으면 충분하다.
- **별도 이름으로 설명할 개념이 생기거나, 두 값 사이에 지켜야 할 규칙이 생기면 별도 타입을 검토한다.** 
  - 예를 들어 시작일과 종료일을 받는 곳마다 순서를 검사한다면, `DateRange`를 만들고 그 타입에서 순서를 보장할 이유가 생긴다.
- 값 복사, 가변성, 크기까지 고려해 `ValueTuple`, `struct`, `class`를 선택할 때는 아래 문서를 다시 본다.
  - :airplane: [05장. Primitive, Reference, and Value Type](../C%23%20Ver_2/05%EC%9E%A5_%20Primitive%2C%20Reference%2C%20and%20Value%20Types/Primitive%2C%20Reference%2C%20and%20Value%20Type.md)

#### :bookmark: 튜플의 도입 과정 실제 Github Issue

> There are many scenarios where you'd like to group a set of typed values temporarily, without the grouping itself warranting a "concept" or type name of its own.

> Other languages use variations over the notion of tuples for this. Maybe C# should too.

> THe declaration is meaningless overhead in itself, and since it doesn't represent a clear concept, it is hard to give it a meaningful name.

:airplane: [Mads Torgersen, Proposal: Language support for Tuples](https://github.com/dotnet/roslyn/issues/347)

#### :pushpin: XML에 저장하는 경우에도 Tuple은 문제없다.

- Codex가 로컬 .NET의 `XmlSerializer`로 두 정수를 담은 튜플 목록을 저장하고 다시 읽었다. 
- 값은 복원됐고, XML에는 `YearMonth`, `CheckCount` 자리가 `<Item1>`, `<Item2>`로 기록됐다.<br>
  XML에 남길 묶음이라면 코드에서 읽는 이름과 실제 저장 파일에 남는 이름을 함께 확인한다.
