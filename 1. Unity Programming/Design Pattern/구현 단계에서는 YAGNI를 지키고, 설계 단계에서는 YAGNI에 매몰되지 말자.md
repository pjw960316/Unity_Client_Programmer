## :fireworks: YAGNI(=You Aren't Gonna Need It)를 고민하게 된 개발 경험

#### :white_check_mark: 이전까지의 생각과 경험

- **언젠가 쓰겠지 식의 과한 설계 -> 뭘 만들음 -> 실력 상승 -> 만든 게 이상한 걸 발견 -> 제거**
  - 최소 10번 이상 경험
- **뭘 만들음 -> 회사 코드에 비슷한 거 있음 -> 제거**
- **개발 → 리팩터링 → 개발 → 리팩터링을 반복하며 전체 개발이 늦어졌던 경험이 있다.**

<br>

#### :white_check_mark: 최근의 경험 및 깨달음

- YAGNI는 정답이 없다.
- 하지만 확실한 건 나름의 규칙이 있어야 한다. -> 유지보수에 큰 도움이 된다.
- 미리 만들어 둔 자료구조 (설계 대충함)를 결국 지운 경험이 있다.
  - 물론 CODEX가 쉽게 해줬다만 구현 및 설계에서 괜히 계속 거슬리게 했다.
- 구현 과정 예시
  - 당시에는 물 마신 횟수를 월별로 보여 줄 일이 없었다. 보여 줘야 할 때 저장을 추가하면 되고, 그때 설계해도 어려울 게 없다고 판단했다.
  - 그때는 ‘나중에 만들기 어렵나’를 기준으로 삼았다. 
  - 지금은 구현 중에 이런 생각이 떠오르면, *설계에서 다시 판단할 문제인지부터 본다.* 검토가 필요하면 구현을 멈추고 노트로 돌아간다.
  - 예전에는 이 구조를 바꾸는 게 어렵지 않아? 그러면 미리 만들지 말자의 방향이었다. <br> 하지만 CODEX 시대에 이건 무의미하다. <br> 그래서 방향을 다르게 잡았고 구현 단계와 설계 단계에서 바라보는 시각의 차이를 두었다.

<br>

#### :speech_balloon: Reddit

> YAGNI" ("You Aren't Gonna Need It" 또는 "You Ain't Gonna Need It")라는 아이디어는 본질적으로 필요하다고 판단될 때까지 기능을 구현하지 말라는 생각입니다. 

> 더 실용적인 측면에서, 이것은 종종 현재 구현하고 있는 기능을 복잡하게 만드는 추상화를 구현하지 말라는 것을 의미합니다. 왜냐하면 실제로 미래에 당신의 추상화를 활용하지 않을 가능성이 높기 때문입니다. 

> 이것의 결과는 종종 해당 특정 기능에 대한 개발 시간이 증가하고, 즉시 이해하기 더 어려운 코드가 됩니다.

## :fireworks: 나만의 YAGNI

#### :white_check_mark: 2 가지로 나누는 개발

- **구현 과정** = Codex + Rider
- **설계 과정** = Codex + 종이노트 + 나의 Github

<br>

#### :white_check_mark: 구현 과정에서는 YAGNI를 철저히 지킨다.

- **구현 과정에서 YAGNI를 지키지 않는다면 검토 없이 무언가를 마구 만들게 된다.**
  - 이는 CODEX 시대에 더욱 위험하다.
  - 구현 과정에서의 *'신내림?'*으로 초고속 판단을 해서 만든 코드는 <br> 대개 폐기되곤 한다.
- **오히려 막 만들다가 이상함을 발견하면 시간이 낭비 된다.**
  - CODEX 시대라 시간이 덜 낭비되지만 의외로 큰 낭비다.

<br>

#### :white_check_mark: 설계 과정에서는 YAGNI에 매몰되지 않는다.

- 필요하지 않은데 괜히 오버 엔지니어링 하는 것도 위험하다. <br> 하지만 필요한데 YAGNI에 매몰되어 만들지 않는 것도 그만큼 위험하다.
- 설계를 꼼꼼하게 하다보면 사실 이게 필요한 지 필요하지 않은지를 검토하게 된다.

<br>

#### :white_check_mark: :star: 중요한 결론 : 구현을 멈추고 설계로 돌아가야 하는 순간

- 완벽한 설계는 있을 수 없다. (적어도 내 실력에서는 팩트다.)
- 구현 도중 슬슬 놓친 점이 보이게 된다. 
  - 흠... ㅈ된 거 같은데  ->  이 때 '구현 단계에서는 YAGNI를 철저히 지킨다.'를 떠올린다.
  - 어서 설계를 검토하러 돌아간다.
- 이 때 깊이 고민하고 미리 만들어 놔야 한다면 만들자.
  - 내가 확실하게 저 기능은 구현이 필요하다면 미리 만들어야지!
