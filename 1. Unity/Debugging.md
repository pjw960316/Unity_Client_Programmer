# 대학 시절 디버거에 대한 생각
- 왜 대학 때 교수님께서 디버거를 잘 쓸 줄 알아야 한다고 강조하셨는지 이제야 알겠다. 내가 원하는 모든 정보를 파악할 수 있다.
- 정보를 알고 개발자가 그에 대한 판단을 내릴 수 있다. 정보를 모르면 개발자는 아무런 판단을 내릴 수 없다.

# :star:디버깅 포인터를 찍어봐야 하는 경우
### 1. 디버깅이라는 이름 값을 하자. 버그를 찾을 때 사용하자.
  - 당연히 이름에 걸맞게 디버깅에 이용해야 하며 개발자가 작성한 대로 값이 올바르게 들어가는 지 파악해야 한다.
  - 내가 코드를 입력하다가 실수 한 부분에 대해서는 로그를 남겨주자.
### 2. 코드 분석과정에서 흐름을 파악하지 못하는 부분
  - 기본적으로 코드 분석에는 디버거를 사용하지 않고 F12와 함께하라고 배웠다.
    - 하지만 그럼에도 불구하고 흐름을 파악하지 못하는 경우가 정말 많다. 이럴 때 우리는 디버거로 코드의 흐름을 파악해야 한다.
  - 코드 흐름 파악
    - 중단점을 한 곳 찍고 천천히 F10으로 읽어본다 -> 중단점을 추가하고 중단점만 읽는다.
    - 어디서 콜이 되는지 모르는 메서드의 경우 콜스택을 읽어 본다.
      - 내부코드나 라이브러리 까지는 읽지 않아도 괜찮다.
  
# 주의 사항
- 아래에 찍을수록 좋은 것은 아니다.
  - 어떤 메서드가 Line_1 ~ Line_50 까지 있다고 가정하자. Line_5의 특정 데이터가 궁금하여 Line_6에 데이터를 찍었다. 그러면 Line_1 ~ Line_6까지 모든 데이터의 값이 디버거에 나온다. Line_50에서 찍으면 Line_1 ~ Line_50까지 모든 데이터의 값이 디버거에 나온다.
  - :star:하지만 Line_50까지 찍으면 Line_5의 데이터가 Line_30이나 Line_37 같은 곳의 코드 때문에 변경될 수 있다. 그러므로 정밀하게 검사하려면 궁금한 부분의 코드 바로 아래에 중단점을 찍자.
 
# 경험을 통한 팁
- 객체의 어떤 행동(ex : 경험치 증가하는 프로그레스 바)의 동작 방식을 이해하기 가장 좋은 방법은 디버거를 이용하고 호출 흐름이 예상 되는 곳에 무작정 중단점을 찍어 보는 것이 도움이 된다.
  - 물론 중단점을 줄이고 콜스택을 보는 것이 더 도움이 되지만 초반에는 무지성 중단점만한게 없다.
- 디버거는 항상 실행하지 않고 자주 껐다가 킨다. 게임이 로드 될 때나 중요하지 않은 시간에 미리 디버거를 켜두면 조금은 시간을 아낄 수 있다.
  - 디버거를 켜놓은 상태에서 게임을 실행하면 정말 오래걸릴 때가 있다.
- 유니티가 멈춰 있을 때 디버거에서 중단되어 있지 않은 지 확인하자.

# 로그를 찍을까? 디버거를 돌릴까?
- 반복문의 경우는 로그가 더 좋은 것 같다.
- 완전히 간단한 정보 같은 경우도 로그가 좋은 것 같다.
  - 하지만 결국 로그는 위의 코드의 실행흐름보다 미세하지만 늦게 호출되므로 약간의 미세오차가 존재한다.
    - ![image](https://user-images.githubusercontent.com/55792986/210022587-a43846e1-c6ee-4bfb-a3f5-54afe9cf197d.png)
        - 0.40000000004
          - 이 값은 0.4보다는 크다.
- 디버거를 사용해도 실행 흐름이 이해가 가지 않는다면 로그를 찍어보는 것도 도움이 된다.

# 디버거 관련 버튼 (라이더)
- ![image](https://user-images.githubusercontent.com/55792986/213981882-e0848c88-8121-4af2-bb9b-d4c75a3a77d9.png)
- F5 : 다음 중단점으로 이동
  - 코드의 흐름을 잘 이해했고 디버깅을 할 때는 매우 좋다.
  - 하지만 코드의 흐름을 잘 이해하지 못했다면 디버깅 포인트를 잘못 찍을 가능성이 매우 높기 때문에 원하는 정보를 알지 못하는 경우가 많다.
- F10 : 다음 블록으로 이동
  - 현재 시점을 기준으로 바로 다음 블록으로 이동한다. 
  - 해당 블록에 메서드가 있어도 메서드를 직접 들어가지는 않는다.
  - **코드 전체 흐름을 파악하기 가장 좋은 기능이다.**
- F11 : 다음 라인으로 이동
  - 현재 시점을 기준으로 바로 다음 라인으로 이동한다.
  - 진짜 한 줄 씩 읽는 기능이다.
  - 메서드나 참조를 만나면 무조건 이동하고 필요 없는 세세한 정보까지 다 찾아서 이동한다.
  - 좀 과하지만 진짜 깊은 코드 분석이라면 이 기능을 이용하자.
  
# 콜스택
- 메서드를 호출하는 부분을 아무리 봐도 찾을 수 없는데 호출 된 경험이 있다. 오랜 시간을 투자해서 이 호출 부분을 찾으려고 노력했으나 실패했다. 알고 보니 디버거의 콜스택을 보면 바로 파악할 수 있었다.
- 호출 순서를 LIFO로 나열해준다.
  - 중단점에 찍힌 부분이 어떻게 호출되었는 지 스택으로 쌓여서 나열된다.
- 보라색은 엔진의 메서드이고, 흰색이 작성한 메서드다.
  - 한 번 쯤은 엔진의 코드를 보면서 왜 이렇게 짰는지 파악하는 경험도 중요하다고 배웠다.
  - 디버깅 하다가 협업 코드를 보면 쉽게 쉽게 이해하지만 유니티 자체 코드로 넘어가면 은근 벙찐다.
    - 유니티 자체 코드는 구글에 자세한 설명이 있으므로 오히려 파악하기 쉬움에도 불구하고.
  - **f12를 눌렀는 데 유니티 제공 메서드면 한 번 구글링을 통해 봐라**
