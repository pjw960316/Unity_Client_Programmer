# 주의 사항
- 아래에 찍을수록 좋은 것은 아니다.
  - 어떤 메서드가 Line_1 ~ Line_50 까지 있다고 가정하자. Line_5의 특정 데이터가 궁금하여 Line_6에 데이터를 찍었다. 그러면 Line_1 ~ Line_6까지 모든 데이터의 값이 디버거에 나온다. Line_50에서 찍으면 Line_1 ~ Line_50까지 모든 데이터의 값이 디버거에 나온다.
  - :star:하지만 Line_50까지 찍으면 Line_5의 데이터가 Line_30이나 Line_37 같은 곳의 코드 때문에 변경될 수 있다. 그러므로 정밀하게 검사하려면 궁금한 부분의 코드 바로 아래에 중단점을 찍자.
 
# 경험을 통한 팁
- 객체의 어떤 행동(ex : 경험치 증가하는 프로그레스 바)의 동작 방식을 이해하기 가장 좋은 방법은 디버거를 이용하고 호출 흐름이 예상 되는 곳에 무작정 중단점을 찍어 보는 것이 도움이 된다.
  - 물론 중단점을 줄이고 콜스택을 보는 것이 더 도움이 되지만 초반에는 무지성 중단점만한게 없다.
- 디버거는 항상 실행하지 않고 자주 껐다가 킨다. 게임이 로드 될 때나 중요하지 않은 시간에 미리 디버거를 켜두면 조금은 시간을 아낄 수 있다.
- 유니티가 멈춰 있을 때 디버거에서 중단되어 있지 않은 지 확인하자.

# 디버거에 대한 생각
- 왜 대학 때 교수님께서 디버거를 잘 쓸 줄 알아야 한다고 강조하셨는지 이제야 알겠다. 내가 원하는 모든 정보를 파악할 수 있다.
- 정보를 알고 개발자가 그에 대한 판단을 내릴 수 있다. 정보를 모르면 개발자는 아무런 판단을 내릴 수 없다.

# 로그를 찍을까? 디버거를 돌릴까?
- 반복문의 경우는 로그가 더 좋은 것 같다.
- 완전히 간단한 정보 같은 경우도 로그가 좋은 것 같다.
  - 하지만 결국 로그는 위의 코드의 실행흐름보다 미세하지만 늦게 호출되므로 약간의 미세오차가 존재한다.

        - 0.40000000004
          - 이 값은 0.4보다는 크다.

# 콜스택
- 메서드를 호출하는 부분을 아무리 봐도 찾을 수 없는데 호출 된 경험이 있다. 오랜 시간을 투자해서 이 호출 부분을 찾으려고 노력했으나 실패했다. 알고 보니 디버거의 콜스택을 보면 바로 파악할 수 있었다.
- 호출 순서를 LIFO로 나열해준다.
  - 중단점에 찍힌 부분이 어떻게 호출되었는 지 스택으로 쌓여서 나열된다.
