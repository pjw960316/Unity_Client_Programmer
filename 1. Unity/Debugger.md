# 사용하면서 느낀 점
- 개발자가 원하는 부분의 모든 정보를 파악할 수 있다.
- 실행 흐름을 파악할 수 있다.

# 주의 사항
- 아래에 찍을수록 좋은 것은 아니다.
  - 어떤 메서드가 Line_1 ~ Line_50 까지 있다고 가정하자. Line_5의 특정 데이터가 궁금하여 Line_6에 데이터를 찍었다. 그러면 Line_1 ~ Line_6까지 모든 데이터의 값이 디버거에 나온다. Line_50에서 찍으면 Line_1 ~ Line_50까지 모든 데이터의 값이 디버거에 나온다.
  - :star:하지만 Line_50까지 찍으면 Line_5의 데이터가 Line_30이나 Line_37 같은 곳의 코드 때문에 변경될 수 있다. 그러므로 정밀하게 검사하려면 궁금한 부분의 코드 바로 아래에 중단점을 찍자.
 
# 팁

- 디버거는 항상 켜놓을 수 없기 때문에 자주 껐다가 킨다. 어지간하면 유니티에서 게임을 로드할 때 디버거를 켜서 테스트 시간을 아끼자.

# 로그 vs 디버깅 포인트
- ![image](https://user-images.githubusercontent.com/55792986/209740156-2432ccd5-56e9-47fd-9f18-3fbe48984917.png)
- 일단 라이더에서 디버그를 켜고 유니티를 실행한다.
- 디버깅 포인트로 디버그를 해보면 해당 변수에 모든 걸 볼 수 있다.
- 디버그는 r_value만 검사하는 것 같다.
- 라이더에서 디버그 진행중이면 유니티 자체에 대한 개발자의 컨트롤이 먹히지 않는다.
- 디버그
  - ![20221228_145340](https://user-images.githubusercontent.com/55792986/209764710-8cc02a4a-f5e3-40f2-9fb1-6352a922d5ce.png)
    - 이거 눌러서
  - 인자로 클래스를 넘겨주면 역시 call by ref
  - 결론 : 디버깅 포인트 잘 찍고 디버거 보는 능력이 좀만 되면 로그는 찍어볼 필요가 없다.
  - 라이더에서 디버그를 하면 아래에는 안나오지만 그 코드 옆에 핵심 정보는 나온다.
  - 개발하면서 계속 디버그 포인트 찍으면서 확인하고 싶은 데이터를 갱신할 수 있다.
- 중요한 생각
  - 디버깅 포인트로 해당 포인트를 일단 찍으면 l_value는 r_value를 계산하지 않고 출력한다. 
  - l_value가 궁금하면 다음 디버깅 포인트를 찍어야 한다. 왜?
